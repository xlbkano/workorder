# 可配置审批流设计说明

## 1. 模型

| 表 | 作用 |
|---|---|
| `approval_flow` | 流程定义：名称、编码、适用工单类型、适用部门、启停状态 |
| `approval_flow_node` | 流程节点：顺序、审批人类型、签核方式（或签/会签）、是否允许自批、无人时是否跳过 |
| `work_order_task` | 审批任务：当前轮次、节点、审批人、任务状态、是否加签 |
| `work_order` | 新增 `flow_id`、`current_node_order`、`round` |
| `work_order_approval` | 审批留痕：动作扩展为通过/驳回/转交/加签，记录节点与轮次快照 |

## 2. 流程匹配

新建工单时按 `工单类型 + 申请人部门` 匹配启用流程，优先级：

1. 类型精确 + 部门精确
2. 类型精确 + 部门不限
3. 类型通用 + 部门精确
4. 类型通用 + 部门不限（兜底）

同一“类型 + 部门”组合只允许一个启用流程；流程编码全局唯一。

## 3. 审批人类型

| 类型 | 含义 | 配置值 |
|---|---|---|
| `DEPT_MANAGER` | 申请人所在部门主管 | 无需填写 |
| `DEPT_ROLE` | 申请人部门内指定角色 | EMPLOYEE / MANAGER / ADMIN |
| `ROLE` | 全局指定角色 | EMPLOYEE / MANAGER / ADMIN |
| `USER` | 指定用户 | 用户 id |
| `USER_LIST` | 指定多人 | 逗号分隔的用户 id |

解析时会自动过滤停用用户；默认排除申请人本人，勾选“允许申请人自己审批”后保留。
若节点解析不到审批人：勾选“找不到审批人时自动跳过”则跳过该节点，否则提交/推进时返回明确提示。

## 4. 签核规则

- **或签（OR）**：节点内任一审批人通过，其余任务置为失效，流程进入下一节点。
- **会签（AND）**：节点内全部审批人通过后才进入下一节点；任一审批人驳回，工单直接驳回。
- **加签**：在当前节点追加审批任务并标记 `add_sign=1`；只要存在加签任务，该节点按会签处理，追加人通过后才可推进。
- **转交**：修改当前任务审批人，节点和轮次不变，记录一条“转交”留痕。

## 5. 状态与动作

```
待审批(1) ──> 审批中(2) ──> 已通过(3)
    │             │
    ├──驳回───────┴──> 已驳回(4) ──重新提交(轮次+1)──> 待审批(1)
    └──撤销──────────> 已撤销(5)
```

- 审批/撤销仅允许在 1、2 状态；
- 重新提交仅允许在 4 状态，由申请人操作，历史任务与审批记录不删除；
- 状态判断集中在 `WorkOrderStatus` 枚举，非法迁移在 Service 层拦截。

## 6. 并发控制

- 审批动作先对工单执行 `SELECT ... FOR UPDATE`，同一工单的审批串行化；
- 任务更新使用 `UPDATE ... WHERE status = 0` 条件更新，重复处理返回“任务已被处理”；
- 工单表保留 `version` 乐观锁；
- 任务表唯一键 `(work_order_id, round, node_id, approver_id)` 防止重复任务。

## 7. 配置入口

管理员登录后进入「流程配置」：

- 查看流程及节点；
- 新建/编辑流程；
- 启用/停用流程；
- 存在审批中工单的流程禁止修改，避免影响在途流程。

接口：`GET/POST /flows`、`PUT /flows/{id}/status`。

## 8. 种子流程

| 流程 | 适用类型 | 节点 |
|---|---|---|
| 通用审批流程 | 通用 | 部门主管 → 管理员 |
| 采购审批流程 | 采购 | 部门主管 → 财务负责人（赵六）→ 管理员 |
| 报销审批流程 | 报销 | 部门主管 → 管理员 |

种子数据位于 `sql/work_order.sql`；存量库使用 `sql/upgrade_approval_flow.sql` 升级。
